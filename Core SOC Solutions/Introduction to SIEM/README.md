# SIEM Alert Investigation Lab

## Overview

This lab gave me practical exposure to how a **SIEM detects and presents suspicious activity through alerts**.

The lab provided a simulated SIEM dashboard containing different security events. When suspicious activity occurred, the activity generated an event that matched the conditions of a previously configured detection rule. Once the rule conditions were satisfied, the SIEM generated an alert.

The purpose of the lab was to investigate the triggered alert, trace it back to the event that caused it, identify the user and host involved, understand which part of the event matched the detection rule, and determine whether the alert represented a **true positive or false positive**.

This provided a practical example of how a SOC analyst can move from a high-level alert to the underlying event and eventually make an assessment about the activity.

## What I Learned

The main concept I learned from this lab is that a SIEM alert is generated when **events match the conditions defined in a detection rule**.

The basic workflow is:

**Activity → Event → Detection Rule → Alert → Investigation → Classification**

An alert itself does not automatically prove that an attack has occurred. It means that some activity matched a rule that was configured to detect a particular condition.

The analyst therefore needs to investigate the event and its context before deciding whether the alert represents legitimate or malicious activity.

## Practical Lab

I worked with a simulated SIEM dashboard containing security-related events.

The lab included a **Suspicious Activity** scenario that generated an alert. After the activity was triggered, I investigated the resulting alert and examined the events associated with it.

The investigation focused on tracing the alert back to the activity that caused it.

### Investigating the Alert

The first step was to identify the **process responsible for triggering the alert**.

After locating the relevant event, the investigation could then be expanded to identify:

* The process that caused the alert
* The event associated with the process execution
* The user responsible for executing the process
* The hostname associated with the user
* The detection rule responsible for generating the alert
* The specific term or condition in the event that matched the rule

This demonstrates why the individual fields inside a SIEM event are important. A single event can contain information about the **process, user, hostname, and other attributes** that help an analyst understand what happened.

## Understanding the Detection Rule

An important part of the investigation was examining the rule responsible for triggering the alert.

Detection rules are generally based on specific conditions or values found within normalized log fields.

For example, a rule may look for a particular process name, command, event ID, username, IP address, or another value.

In this lab, I examined the rule alongside the suspicious process to determine **which term in the event matched the rule condition**.

This helped demonstrate the relationship between:

**Event Field → Matching Value → Detection Rule → Alert**

Understanding this relationship is important when investigating why a SIEM generated an alert.

## Identifying the User and Host

The investigation also required identifying the **user responsible for the process execution** and the **hostname associated with that user**.

This is important because knowing what process executed is only part of the investigation.

An analyst also needs to establish:

* **What happened?**
* **Which process was involved?**
* **Who executed it?**
* **Which system was involved?**
* **Why did the SIEM consider it suspicious?**

Connecting these details provides more useful context than looking at the process alone.

## True Positive vs False Positive

After examining the alert and its associated event, the final classification was whether the alert represented a **True Positive** or **False Positive**.

### True Positive

A true positive means the detection correctly identified activity that matched the behavior the rule was designed to detect.

### False Positive

A false positive occurs when the detection rule triggers, but the activity turns out to be legitimate or otherwise not malicious.

This distinction is an important part of SOC alert triage because not every alert represents an actual security incident.

## Alert Investigation Process

The investigation in this lab can be summarized as:

1. **Trigger the suspicious activity**

   * Generate the activity that causes the SIEM detection rule to evaluate the resulting events.

2. **Locate the triggered alert**

   * Identify the alert generated by the SIEM.

3. **Identify the responsible process**

   * Examine the alert and associated events to determine which process caused the detection.

4. **Find the relevant event**

   * Locate the event containing the process execution information.

5. **Identify the user**

   * Determine which user account was responsible for executing the process.

6. **Identify the hostname**

   * Determine which endpoint or system was involved.

7. **Examine the detection rule**

   * Understand the conditions used by the SIEM rule.

8. **Identify the matching term**

   * Compare the suspicious event with the rule and determine which value caused the rule to match.

9. **Classify the alert**

   * Determine whether the detection represents a true positive or false positive based on the available evidence.

10. **Review the resulting action**

* The lab also demonstrated how selecting the appropriate action in the investigation workflow reveals the final result.

## Key Takeaways

* SIEM alerts are generated when **events satisfy detection rule conditions**.
* Investigating an alert requires going beyond the alert itself and examining the underlying event.
* Process execution information can help identify what activity triggered a detection.
* User information helps establish who was responsible for the activity.
* Hostname information identifies the system where the activity occurred.
* Examining the detection rule helps explain **why the SIEM generated the alert**.
* Matching a specific term or value to a rule condition is an important part of understanding a detection.
* Alerts need to be investigated before being classified as **true positives or false positives**.
* A SIEM provides the centralized visibility needed to connect these pieces of information together.
